# Code review for acf-i18n

## What kind of repo this is

This is a translation-data repository, not an application. The overwhelming majority of "bugs" here are wrong or corrupted _content_ in locale JSON files, not logic bugs in the handful of `.mjs` pipeline scripts. Review both, but weight your attention accordingly — a diff that touches 40 locale files and 1 script file needs far more scrutiny on the 40 than the 1.

Ground truth for how this repo works is `/CLAUDE.md` at the repo root — read it if it's not already in context. Key facts repeated here because they change what counts as a bug:

- `src/locales/en/{web,messages}.json` are the only files a human should ever hand-edit. Every other locale is machine-generated by `npm run web` / `npm run message`, which use `@google-cloud/translate` through `src/translate.common.mjs`, with fixed terms enforced by `src/glossary.mjs`.
- `web.json` (options page) and `messages.json` (Chrome extension, `chrome.i18n` format) are reviewed **separately** — a change to one says nothing about the other.
- Locale folder names must be codes Chrome's extension i18n actually recognizes (https://developer.chrome.com/docs/extensions/reference/api/i18n). A folder using an unrecognized code (a bare `pt` instead of `pt_PT`, `kk` which isn't on Chrome's list at all) is a real, silent bug: `messages.json` under it will simply never load in the extension. Check `src/translate.constant.mjs`'s `LANGUAGES` list against Chrome's official list when locale folders change.

## Review checklist for locale file changes

For every changed key in every changed locale file:

1. **Structure** — does `npm test` pass? It already checks missing/extra keys, `{{name}}`/`$1` placeholder integrity, `<N>...</N>` and named-tag integrity (count, pairing, balanced nesting), and leaked internal pipeline tokens (`zzPHzz`, case-mutated or transliterated variants). Don't re-derive these checks by hand — run the suite, then focus review time on what it can't catch.
2. **Glossary compliance** — does the translation match `glossary.mjs`'s canonical rendering for any term it contains? If the string is an exact standalone match for a glossary term, it must equal the glossary's value for that language, not something Translate produced independently.
3. **Semantic accuracy** — read the English source and the translation side by side. High-value defect classes found repeatedly in this repo's history, worth specifically checking for:
   - **Reversed meaning** (a negation or polarity flip — "not invalidated" instead of "invalidated").
   - **Wrong sense of an ambiguous English word** ("Auto" → car instead of automatic; "Docs" → doctors instead of documents; "Export"/"Import" in the customs sense instead of the data sense).
   - **Duplicated concept** — the same idea expressed twice in one string (a raw untranslated fragment plus a natural restatement of the same idea), a signature of a term getting cut out of a sentence for separate handling.
   - **A raw camelCase/identifier-looking string shipped as UI text** (e.g. `RecheckOption` instead of a real translated label) — this is usually an English _source_ bug, not a translation bug: fix `en/messages.json` or `en/web.json`, not just the target locale.
4. **Placeholder semantics, not just presence** — a placeholder token can survive translation while the surrounding text implies it means something different than the source implies (a `$1` meant as a location translated with wording that implies it's a price). Read what the sentence around the token actually claims.
5. **Tag-boundary drift** — a closing tag (`</kbd>`, `</1>`, etc.) that has moved to swallow extra translated text or punctuation that should be outside it. `npm test`'s nesting check catches malformed/orphaned tags, but not a tag that's still well-formed while covering the wrong span — read the actual translated string.
6. **Compare against git history**, not just the English source, when a PR _regenerates_ locale files rather than hand-editing them. A full retranslation run can regress a string that was already correct before (`git diff` against the base branch, or `git log -p -- <file>` on the specific key, shows whether a flagged string used to be right and this PR broke it — that changes the fix, and sometimes the root-cause diagnosis, e.g. a pipeline logic bug rather than a one-off mistranslation).

Do not trust a review report (yours, a bot's, or a pasted external audit) against your memory of the repo's state — always re-check the _current_ file content directly before fixing or replying. This repo's history has several cases of a review being accurate when written but stale by the time it was acted on (a prior fix already landed, or the flagged run hadn't actually completed yet).

## Responding to PR review comments (Copilot, CI bots)

When a `ci-monitor-event` or similar notification reports new review comments on a PR in this repo:

1. Pull the comment bodies and IDs: `gh api repos/Dhruv-Techapps/acf-i18n/pulls/comments/{review_id}` for the summary, or `gh pr view {number} --json comments` / the specific `comment_id`s given in the notification.
2. Verify each comment against the actual current file content (checklist above) before agreeing with it — bots are sometimes right about a defect but wrong about the fix, or flag something already fixed in a later commit than the one they reviewed.
3. Fix confirmed issues, commit, and push to the PR's existing branch (do not force-push, do not open a second PR for the same branch).
4. Reply to each addressed inline comment **in its own thread** — not a general PR comment. The endpoint is easy to get wrong: it needs the PR number in the path, not just the comment ID.
   ```bash
   gh api repos/Dhruv-Techapps/acf-i18n/pulls/{pr_number}/comments/{comment_id}/replies \
     -f body="What changed and why.

   _🤖 Addressed by [Claude Code](https://claude.com/claude-code)_"
   ```
   (`repos/.../pulls/comments/{id}/replies`, without the PR number, 404s.)
5. Resolve each addressed thread. GitHub's REST API has no resolve endpoint — it's GraphQL-only. Find the thread ID first (it is NOT the comment's `databaseId`):
   ```bash
   gh api graphql -f query='
   query {
     repository(owner: "Dhruv-Techapps", name: "acf-i18n") {
       pullRequest(number: {pr_number}) {
         reviewThreads(first: 50) {
           nodes { id isResolved comments(first: 1) { nodes { databaseId } } }
         }
       }
     }
   }' --jq '.data.repository.pullRequest.reviewThreads.nodes[] | "\(.id) \(.isResolved) \(.comments.nodes[0].databaseId)"'
   ```
   Match the `databaseId` in that output to the `comment_id` you replied to, then resolve that thread's `id`:
   ```bash
   gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "THREAD_ID"}) { thread { isResolved } } }'
   ```
6. Skip replying to comments you didn't act on (a false positive, or out of scope) — say why inline in your own summary to the user instead of resolving or replying on GitHub for those.

## Constraints specific to this environment

- The translate scripts (`npm run web`, `npm run message`) need GCP credentials at a path outside the repo (`~/Documents/serviceAccountKey.json` per the constructor in `translate.common.mjs`). A sandboxed environment usually can't reach that path (`EPERM`) — if a fix requires regenerating translations rather than a direct hand-edit to a target locale JSON file, say so explicitly and ask the user to run the script themselves, rather than silently attempting it or silently skipping the retranslation.
- `en/` edits are the only edits that survive future regeneration automatically (the cache reuses a target file's existing value as long as its recorded English source matches — a hand-edit to a target locale file persists on its own as long as `en/` for that key doesn't change). Prefer fixing `en/` over hand-patching 22 target files when the defect traces to ambiguous or malformed English source text.
